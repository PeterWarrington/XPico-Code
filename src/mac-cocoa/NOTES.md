# Cocoa port (Mac OS X 10.4, PowerPC)

The same approach as `src/mac-carbon`: the app in `src/*.c` is not touched, and
this directory implements the Win32 surface it is written against. Only the
substrate differs — Cocoa, Quartz and POSIX instead of QuickDraw and the Carbon
Event Manager.

Build it with `tools/build_mac_cocoa.sh`, which needs a toolchain that can
still emit PowerPC code: Xcode 2.x or 3.x with the 10.4u SDK, either natively
on a PowerPC Mac or cross-compiling from an Intel one. Clang cannot — PowerPC
support was removed long ago. `tools/build_mac_cocoa.sh --host` builds the same
sources for whatever machine you are on, which is how to try a change without a
Tiger box to hand.

## Files

| file | what it holds |
| --- | --- |
| `win32.h` | the Win32 surface, the name traps, `MAX_PATH` 512 |
| `cocoamain.m` | `main()`: autorelease pool, `NSApplication`, `finishLaunching`, then `WinMain` |
| `wnd.m` | window/child table, the `XPView` and delegate, the event pump behind `GetMessage` |
| `gdi.m` | GDI over `CGContext`: DCs, offscreen bitmaps, text, shapes, the caret |
| `sys.m` | ini files, clipboard, menus, dialogs, directory walks, file watches |
| `compat.m` | file I/O, memory, environment, cursors, `NSWorkspace`, string spellings |
| `edit.c` | the single-line EDIT control — the Carbon one, app-side only |
| `panel_cocoa.c` | Problems/Output/Terminal panel, in place of `terminal.c` |
| `term_pty.c` | the shell: `forkpty` in process |
| `Info.plist` | bundle metadata; `@VERSION@` comes from `APP_VERSION` at build time |
| `XPicoCode.icns` | generated by `tools/make_icns.py`; checked in |

## What this port has to get right

**The window model is the Carbon port's.** One `NSWindow` with one `NSView`;
the six child HWNDs are lightweight rectangles drawn into that view with a
clipped, origin-shifted HDC. Keeping it identical is what made the rest small.

**`BOOL` is the name trap of this port.** `<objc/objc.h>` defines it as
`signed char`, and a second typedef is an error rather than a shadowed name, so
`win32.h` makes it a macro alongside the QuickDraw renames. The cost: the
Objective-C methods in the shim that override AppKit ones are written as
`signed char`, which is what AppKit declares. `Class` is the other one — that
is the Objective-C runtime's own type, so the window-class struct is
`WinClass`.

**`DWORD` and `LONG` are exactly 32 bits**, as they are on Win32 — not
`unsigned long`, which is 64 on any 64-bit host. The target is 32-bit PowerPC
where the two agree, but `GetDIBits` fills arrays the app has sized itself, so
the width has to be the Win32 one. `WPARAM`, `LPARAM` and the `_PTR` types stay
pointer-sized, as they are on Win32 too.

**Coordinates.** `XPView` is `isFlipped`, so the app's rects go straight
through. Offscreen contexts are flipped once at creation, so every primitive is
written in the app's own coordinates. Text then needs
`CGContextSetTextMatrix(ctx, CGAffineTransformMakeScale(1, -1))` or the glyphs
come out mirrored.

**Text takes one of two paths.** `CGContextShowText` is much the cheaper and an
editor draws a great deal of text, but it only encodes Mac OS Roman, and this
system's bytes are UTF-8. So an ASCII run — nearly all source code, and where
the two encodings agree — goes through Core Graphics, and anything else is
decoded and drawn as an `NSString`. The font is named outright
(`LucidaGrande`, `Monaco`) rather than asked for as "the system font", because
`CGContextSelectFont` has to look it up again by name; a hidden system font
like `.AppleSystemUIFont` draws nothing at all, so a name beginning with a dot
sends everything down the AppKit path.

The caret-drift trap from the Carbon port applies here in another form: Quartz
advances are fractional (Monaco at 14pt is 8.4px) while the editor assumes an
integer cell. `CGContextSetCharacterSpacing` pads each fixed-pitch glyph out to
the whole pixel the editor was told about.

**The editor is byte-oriented** — one byte is one character for its caret and
column arithmetic — so a multi-byte character draws correctly but counts as
several columns. Making that whole-character means changing `editor.c`, which
is not this port's business.

**A window DC is a bitmap, not the view.** A `CGContext` is write-only, and
`draw_icon` reads its destination back to blend against. So window painting
goes into a window-sized bitmap that `gdi_end_window_paint` copies to the view.
That bitmap follows the display's scale, which `wnd.m` gets by asking the
window for `backingScaleFactor` by name at runtime — the selector is five years
newer than this target, and on Tiger the answer is 1. The app's own
double buffers follow the same scale, or everything the panels draw is rendered
at half resolution and scaled up.

**The terminal is real.** 10.4 has `fork`, so `term_pty.c` runs a login shell
in a pty in process and the `xpcode-termd` helper the Carbon build needs is not
in the picture.

## Shared code this port changed

- `src/xpcode.h`: a `MAC_COCOA` branch inside the existing `MAC_OS` one —
  POSIX paths, LF line endings, UTF-8, the terminal always available. Build
  with `-DMAC_OS -DMAC_COCOA` so the shared `#ifdef MAC_OS` paths still apply.
- `src/main.c`: `ABOUT_TECH` in place of the hardcoded "QuickDraw and Carbon";
  `PATH_SEPS` instead of a hardcoded backslash in `locate_settings`; and an
  `ICONS_ANTIALIASED` early-out in `draw_icon`, because the supersampling there
  is a way round GDI's hard-edged strokes and Quartz has no such problem.
